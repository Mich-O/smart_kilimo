# Deploying Smart Kilimo (Render)

This covers both demos: Demo A (the hosted web app) and Demo B (Africa's
Talking's own USSD/SMS simulator pointed at the same hosted backend).

## 0. Styling: compiled CSS, not the Tailwind CDN

`static/tailwind.css` is a **compiled, committed file** — Render's build
(`pip install -r requirements.txt`) never touches Node or npm. That file
was generated once from `tailwind.config.js` + `static/src/input.css`
against every class actually used in `templates/**/*.html`.

**If you edit any template and use a new Tailwind class that isn't
already in `static/tailwind.css`, it won't render until you rebuild:**

```bash
npm install        # first time only
npm run build:css  # regenerates static/tailwind.css
```

Commit the updated `static/tailwind.css` alongside your template changes.
There's no build step on Render itself — what's committed is what ships.

## 1. Prerequisites

- This repo pushed to GitHub.
- A free [Render](https://render.com) account (no card required).
- A free [Africa's Talking](https://account.africastalking.com/auth/register)
  sandbox account — you'll need the **username** (usually `sandbox`) and an
  **API key** from the dashboard, for Demo B.

## 2. Deploy the web service + database

1. In Render: **New → Blueprint**, connect this GitHub repo. Render reads
   `render.yaml` and provisions a web service and a free Postgres database
   together, wiring `DATABASE_URL` between them automatically.
2. Render will prompt for the env vars marked `sync: false` in
   `render.yaml` — fill these in:
   - `AT_USERNAME`, `AT_API_KEY` — from your Africa's Talking sandbox.
   - `AT_SENDER_ID` — **leave this blank unless you've actually registered
     a shortcode or alphanumeric ID with Africa's Talking.** An
     unregistered sender ID doesn't raise a clear error; Africa's Talking
     just returns an empty `Recipients` array, which our code logs as
     `AT SMS not accepted: no recipients in response`. Leaving it blank
     makes the SDK omit the `from` field entirely, so AT falls back to
     your account's default sender identity, which always works.
   - `DEFAULT_ADMIN_USERNAME`, `DEFAULT_ADMIN_PASSWORD` — the admin account
     that gets seeded on first boot. Pick a real password here; it's the
     only account you'll be able to log in with initially.
   - `FLASK_SECRET_KEY` and `INTERNAL_API_TOKEN` are auto-generated by
     Render (`generateValue: true`) — you don't need to set these.
3. Deploy. First boot runs migrations-equivalent (`init_db()` creates every
   table), seeds the crop/region/stage reference data, and seeds the one
   admin account from step 2.
4. Visit `https://<your-app>.onrender.com` — you should see the landing
   page. Log in at `/admin/login` with the credentials from step 2, then
   **change that password immediately** via the account menu → it's the
   only credential that ever touched an env var in plaintext.

**Note on the Python version pin:** `render.yaml` sets `PYTHON_VERSION`
explicitly (also mirrored in `.python-version`). This isn't decorative —
without it, Render uses whatever it currently treats as the default for
new services, which drifts over time. SQLAlchemy 2.0.36 crashes under
Python 3.14 (`Mapped[Optional[str]]`-style columns raise a `typing.Union`
`TypeError` during declarative mapping) — this took down a real deploy
before the pin was added. If you ever bump the Python version here,
confirm the full test suite still passes on it first.

## 3. Demo A — the web app

Nothing further needed. Farmers self-register at `/farmer/register`;
admins log in at `/admin/login`. Everything (registration, plot tracking,
notifications, the admin operations tools) runs against the same hosted
Postgres instance.

## 4. Demo B — Africa's Talking simulator

1. In the Africa's Talking sandbox dashboard, under **USSD**, create a
   channel and set its callback URL to:
   `https://<your-app>.onrender.com/ussd`
2. Under **SMS**, set the inbound/callback URL to:
   `https://<your-app>.onrender.com/sms/callback`
3. Open the [AT USSD Simulator](https://developers.africastalking.com/simulator),
   enter your sandbox phone number and the service code you configured,
   and dial in — you're now exercising the exact same `core/ussd_session.py`
   state machine as Demo A, just over AT's real USSD transport instead of
   a browser form. **Use a Kenyan-format number for the simulator's phone
   number field** — `+254` followed by `7` or `1`, then 8 digits (e.g.
   `+254712345678`) — the same shape the web app's registration form
   enforces (`api/forms.py`). Farmer accounts are keyed by phone number, so
   sticking to this format is what lets a number registered through the
   web app and one dialed in through the simulator refer to the same
   farmer.
4. To see an alert actually arrive, either wait for the real 06:00 EAT
   scheduled cycle, or log in as admin and use **Tools** to push that
   plot's deficit over threshold on demand — the resulting SMS goes out
   through the same `AfricasTalkingClient.send()` path either way.

## 5. Known constraints on Render's free tier

- **Spin-down.** The free web service sleeps after ~15 minutes of no
  traffic and takes 30–60s to wake on the next request. Fine for grading;
  just expect the first click after a break to be slow.
- **The scheduler won't fire reliably while asleep.** APScheduler's 06:00
  EAT job only runs if the process is awake at that moment. Use the admin
  **Cycle** page's "Run cycle now" button as the reliable way to
  demonstrate the real production code path, or upgrade to a paid instance
  if you need the literal scheduled trigger to fire unattended.
- **Single worker, on purpose.** `render.yaml` sets `--workers 1`. Don't
  raise this without adding an external lock around the scheduler first —
  see the comment in `scheduler/jobs.py`.

## 6. Demo data on boot

`render.yaml` sets `SEED_DEMO_DATA=true`, so `scripts/seed_demo_data.py`
runs automatically before gunicorn starts (chained in `startCommand` --
Render's `preDeployCommand` is a paid-tier-only feature, so this uses the
free-tier-compatible approach instead). It creates four sample farmers
with a few days of simulated history, so an assessor sees a populated
dashboard immediately rather than an empty one on first login. It's
idempotent (skips farmers that already have an account) and defensive
(a failure in seeding is logged and swallowed, never blocks the real app
from starting) — see the comments in the script and in `render.yaml`.

Set `SEED_DEMO_DATA=false` in your Render environment variables once you
no longer want fake accounts created, e.g. before handing this off as a
real production deployment.

## 7. Rotating the admin password later

`ensure_default_admin()` only seeds an admin account if none exists yet —
changing `DEFAULT_ADMIN_PASSWORD` after first deploy has no effect on an
already-created account. Use the in-app **change password** page
(`/account/password`) while logged in instead.
